Both approaches have trade-offs. Here's the comparison:

## Current Design Difference

| Aspect | `Sudoku` (class) | `SudokuDLX` (static) |
|--------|------------------|---------------------|
| **State** | Holds `_grid`, `_solution`, `_solved`, bitmasks | Stateless — takes `puzzle`, writes to `solution` |
| **Usage** | `Sudoku s(puzzle); s.solve(); s.Draw(false);` | `SudokuDLX::solve(puzzle, solution); SudokuDLX::Draw(solution, false);` |
| **Reusability** | Must create new instance per puzzle | Reusable, thread-safe |
| **API** | OO, stateful | Functional, stateless |

## Which is Better?

**For a library/API: `SudokuDLX` (stateless) is better**
- Thread-safe, no hidden state
- Easier to test — pure functions
- Composable — works with any grid source
- No object lifetime management

**For a UI/app with workflow: `Sudoku` (stateful) can be convenient**
- Holds puzzle + solution together
- Can inspect intermediate state (`_rows`, `_cols`, `_boxes`)
- `Draw(bool)` toggles start/solution naturally

## Recommendation: Unify to Stateless (SudokuDLX style)

The stateless approach is more idiomatic modern C++ for algorithms. You could refactor `Sudoku` to:

```cpp
class Sudoku {

    Sudoku(const Grid& puzzle) : _puzzle(puzzle) {}
    bool solve() { return solve(_puzzle, _solution); }
    void Draw(bool start = true) const { Draw(start ? _puzzle : _solution, start); }
    const Grid& getSolution() const { return _solution; }
    const Grid& getPuzzle() const { return _puzzle; }

private:
    Grid _puzzle;
    Grid _solution;
};
```
